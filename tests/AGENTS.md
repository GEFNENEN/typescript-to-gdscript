# Test harness notes

What the fixture harnesses guarantee and why. The project overview is `PROJECT.md` at the repo root.

- **Fixture programs must load the Godot typings, or every checker-driven branch is half-tested.** `tests/converter/ts-to-gd.test.ts` used to call `convertTsToGd` without a `tsConfigPath`, so `createTsProgram` built a one-file program in which every engine name resolved to nothing — fixtures then only ever exercised the "unresolved, leave it alone" side of each test, while a real project loads the typings and takes the other side. That is how `Vector2(x, y)` shipped as `Vector2.call(x, y)` with all 33 fixtures green AND `fixtures-godot-validate` green (the latter feeds Godot the checked-in EXPECTED `.gd`, which was correct — it never sees the converter's actual output for a typings-aware program). CLOSED: the harness now builds ONE program over every fixture plus `typings/` (`tests/fixtures/ts-to-gd/tsconfig.json`, passed as `program` so the typings parse once — the suite got ~7× faster as a side effect), so fixtures exercise the resolved side and `operators` / `strings` / `variables` fail without the `.call()` fix. Closing it immediately surfaced two more: `-> Callable` was dropped because `type Callable = Function` hit the type-alias rule before the registry check (fixed by asking the registry first), and `gd.getset` value-type inference now yields `float` where it used to yield `int` (see PROJECT.md → Type-Environment Dependencies §4). Any NEW checker-driven decision is only half-tested until a fixture exercises it with the typings loaded
- **Fixture INPUTS must type-check as written.** The same harness also asserts that each `tests/fixtures/ts-to-gd/*.ts` has zero TypeScript diagnostics (`type-checks as written: <fixture>`, via `collectTsDiagnostics` — same program, same `strict` config, same `NOISE_CODES` filter as a real project's checker). Before this, converting and comparing never type-checked the input, so fixtures could pin the conversion of TS no user could write, and 12 did: undeclared fields, `null` in non-nullable slots, an object literal written to a key it lacked, a `Callable` stored into an arrow-typed field. One hid INVALID GDScript: `operators` read `this.v1` without declaring it, so Godot saw a dynamic `self.v1` and could not tell that `v1 - 2 * 1` subtracts an `int` from a `Vector2` — declaring `v1: Vector2` made Godot reject the line at parse time. Real projects also load GENERATED script typings, which this program does not (they cannot be generated for this directory — 16 fixtures share `class_name MyClass`), so the shapes fixtures rely on are mirrored by hand from `content-generators.ts` in `*.gd.d.ts` files next to them: the global script wrapper and a `GodotResources` entry (`super-script-parent.gd.d.ts`, so `extends preload("res://super-script-parent.gd")` is a constructor type rather than `Resource`) and the statics merge (`merged-namespaces.gd.d.ts`, so `this.FIRST` resolves as it does in a project). Such a mirror is a copy and can drift from the generator; keep it to the shape a fixture needs. No exemption list: every fixture was made clean without changing what it tests (`throw 'boom'` instead of `throw new Error(...)` in `unsupported-body`, `(x: any, y: any)` for `gd.match` bindings whose guard does arithmetic). Two program-level checks close its blind spots: every collected diagnostic must sit under a fixture's own key (a file spelled differently, or a `.ts` that is no fixture, would otherwise pass every per-fixture lookup unseen), and the hand-written `*.gd.d.ts` mirrors are type-checked directly, since `collectTsDiagnostics` skips declaration files as a real project's checker does.
- **GD→TS OUTPUT must type-check — as the pipeline produces it, not as the emitter prints it.** `tests/converter/fixtures-gd-to-ts-project.test.ts` copies every `tests/fixtures/gd-to-ts/*.gd` (and `*.tscn`) into one temp Godot project, runs the real `initial-convert-gd-to-ts` CLI over it, and type-checks the result with `collectTsDiagnostics`. It has to be the whole pipeline: the fixture runner pins only the EMITTER's text, but a user gets conversion + import injection + generated script and scene typings + the `runTsHelpers` post-pass, and the post-pass alone repairs whole classes of emitter output (operator errors become `gd.ops`, variant errors `gd.as`). Checked against the emitter text, `Array + Array` in a `var` initializer looks like a converter bug; checked against the pipeline it is fixed — as long as the project's `tsconfig.json` loads the engine typings, which the helpers read from the project root. Non-strict on purpose: GD→TS output is migration output a human finishes, so an untyped GD parameter legitimately comes out untyped. What it catches is output TypeScript cannot resolve at all. Its first run found one in the product: import injection listened only for TS2304 / TS2503, and missed the "Did you mean" forms (2552 / 2833) TypeScript reports when a similar name is in scope — `class Enemy2 extends Enemy` shipped without its import. The fixture SOURCES are real GDScript for the same reason (output can only be judged against valid input): `health` was read undeclared in three fixtures, `operators.gd` subtracted an `int` from a `Vector2` and mixed tab and space indentation, `annotations.gd` redefined `Node.name`, `self2.gd` called `add_spacer()` / `add_recent_preset()` without their required argument, and `extends-path.gd` extended a script that did not exist. That first pass was done by hand and missed six (a code review ran Godot over every source): `abstract.gd` gave its `@abstract` functions bodies, `comments.gd` mixed spaces and tabs in a statement, `enums.gd` returned a value from `_ready`, `functions.gd` inferred a parameter from `:= null`, `variables.gd` redefined `Node.name`, and `dict-generics.gd` declared nested typed collections, which Godot does not support at all — those three members are gone rather than kept as input no project can contain. So the claim is now enforced: the test's second case imports the same project and runs `validateGdFiles` over every source, with its own exhaustive `EXPECTED_GODOT` (again only `self2`). Scripts whose node paths type only through a scene have a minimal `.tscn` beside them (`annotations`, `expressions`, `inherit-user-base`) — `$Label` is a `Node` until a scene says `Label`. The fixture runner ignores `.tscn`, and the converter reads no scene itself (signal handlers arrive through options), so the scenes change nothing it pins. Deliberate diagnostics are listed in `EXPECTED`, matched exhaustively both ways; the only one is `self2`'s `get_joint_bone`, a name nothing resolves, which pins that the converter leaves it bare rather than inventing a `this.`
- The ts-plugin test's wait for `cache.json` (written fire-and-forget by `saveAsync()`) is a poll bounded at 10 s. The bound only matters when the write is slow, and at 2000 ms it ran out on a loaded machine (a demanding app running alongside the suite) on a write that did land. A worker cap was tried for the same episode and reverted: the flakes were that external load, and with the machine idle the suite is clean and fastest on every core
- **Converter diagnostic fixtures** (`tests/fixtures/converter-diag/*.ts` + `.json`, runner in `tests/converter/converter-diag.test.ts`): the `.json` is EXHAUSTIVE in both directions — every entry must match a distinct diagnostic AND no error/warning may be left unaccounted for. That is what lets a fixture assert "reported once" (a rule firing twice leaves one unconsumed) without a hand-written test beside it. `type-error` / `info` need not be listed; they do not block the `.gd` write. Making it strict surfaced four fixtures that were under-specified (`anon-inner-outer-ref`, `file-scope-conflict`, `multiple-classes`, `string-enum` each report two distinct diagnostics, not one).
- **Addon declaration fixtures** (`tests/fixtures/addon-declarations/*.gd` + `.d.ts`, runner `tests/typings/addon-declaration-fixtures.test.ts`) pin what the FULL addon pipeline writes, not the declaration emitter alone: every fixture goes into one throwaway project under `addons/Fixtures/` and `generateAddonTypings` runs once, so fixtures reference each other by `class_name` or `preload` the way addons in a real project do. Cross-addon cases only fail that way — the temp-path leak shipped because no fixture consumed a script WITHOUT `class_name` (`anonymous-preload-consumer` now does). The set must produce zero diagnostics. The directory is kept out of `tests/fixtures/tsconfig.json` (the editor's view of the fixtures): its `.d.ts` are expected output, and without the `.gd.d.ts` the pipeline writes beside them their cross-addon references don't resolve
- `tests/yield-between-tests.ts` (a vitest `setupFiles` entry) awaits one `setImmediate` after every test. Vitest yields only microtasks between tests, so a worker reads the replies to its `onTaskUpdate` RPC calls only when the event loop gets a turn; a file of synchronous tests that build TypeScript programs (the addon pipeline tests are the heaviest) ran past the 60 s RPC timeout under full-suite load, and the run exited 1 with `Timeout calling "onTaskUpdate"` while every test passed. This is the suite's own load, unlike the ts-plugin flake above: master's suite ran clean on the same machine at the same time, and the merged addon tests failed 2 of 2 runs without the yield, 0 of 2 with it
